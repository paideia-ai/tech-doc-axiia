  ---
  Schema.Class vs Schema.Struct — pros and cons

  Schema.Struct (what most of our schemas use):
  Pros: Pure data — no behavior, easy to reason about
  Cons: No computed properties; derived values must live elsewhere
  ────────────────────────────────────────
  Pros: Composes freely (nest, union, intersect)
  Cons: No instanceof check — it's just a plain object
  ────────────────────────────────────────
  Pros: Lighter — no class prototype overhead
  Cons: If you want methods, you end up writing free functions
  Schema.Class (what JSONScores uses):
  Pros: get properties for derived data (ability_scores, totals) — computed on
    access, never serialized
  Cons: Heavier abstraction; class instances, prototypes
  ────────────────────────────────────────
  Pros: instanceof JSONScores works for runtime type checks
  Cons: Composes less naturally — you can't Schema.Union two Classes easily
  ────────────────────────────────────────
  Pros: Methods can encapsulate invariants alongside the data
  Cons: Getters are invisible to Schema.encode — can confuse people expecting
    them in JSON
  ────────────────────────────────────────
  Pros: Self-documenting: the derivation formula lives with the data
  Cons: Testing is trickier: you must decode to get an instance, can't just
    spread a plain object
  When to use which:

  - Struct for plain data bags — ProblemGrade, GradeThresholds, Curve,
  CurvedScores. No behavior needed, just shape + validation.
  - Class when a type has derived values that shouldn't be stored. JSONScores is
   the textbook case: ability_scores and totals are computed from problem_scores
   — storing them would create a consistency risk (stale derived values). The
  getter pattern guarantees they're always fresh.

  In our codebase, only JSONScores genuinely benefits from Class. Everything
  else is pure structure, so Struct is the right default.

  ---
  Schema.extend explicitly rejects Class schemas. Here's the proof:

  // Struct + Struct — works
  const S1 = Schema.Struct({ a: Schema.String });
  const S2 = Schema.Struct({ b: Schema.Number });
  Schema.extend(S1, S2); // ✅ { a: string, b: number }

  // Class + Struct — throws
  class Foo extends Schema.Class("Foo")({ a: Schema.String }) {}
  Schema.extend(Foo, Schema.Struct({ b: Schema.Number }));
  // ❌ "Unsupported schema or overlapping types"
  // "cannot extend Foo with { readonly b: number }"

  // Class + Class — also throws
  class Bar extends Schema.Class("Bar")({ b: Schema.Number }) {}
  Schema.extend(Foo, Bar);
  // ❌ "cannot extend (Foo (Encoded side) <-> Foo) with (Bar (Encoded side) <->
   Bar)"

  Why: The https://effect.website/docs/schema/classes/ state that "Class schemas
   transform a struct schema into a declaration schema." Schema.extend only
  works on Structs (or refinements of Structs). Once a Struct becomes a Class,
  it's a declaration/transformation schema — a different AST node type that
  extend doesn't support.

  Union does work — Schema.Union(Foo, Bar) compiles and decodes correctly,
  producing proper instanceof instances. So my original statement was too
  strong. The accurate version:
  ┌───────────────────────────────────────┬────────┬───────────────────┐
  │               Operation               │ Struct │       Class       │
  ├───────────────────────────────────────┼────────┼───────────────────┤
  │ Schema.extend(A, B)                   │ works  │ throws at runtime │
  ├───────────────────────────────────────┼────────┼───────────────────┤
  │ Schema.Union(A, B)                    │ works  │ works             │
  ├───────────────────────────────────────┼────────┼───────────────────┤
  │ Schema.Record, Schema.Array embedding │ works  │ works             │
  └───────────────────────────────────────┴────────┴───────────────────┘
  The real limitation is extend (merging fields from two schemas), not union.
  For our codebase, this matters if you ever want to build a schema by composing
   smaller pieces — something Struct supports freely.

  Sources:
  - https://effect.website/docs/schema/classes/
  - https://github.com/Effect-TS/effect/issues/4762

⏺ Here's what the broader community discussion reveals, mapped to FP concepts:

  ---
  The FP framing: Effect's data modeling = ADTs in TypeScript

  In classic FP (Haskell, OCaml), data modeling uses two constructs:
  - Product types — all fields present simultaneously (data User = User String 
  Int)
  - Sum types — exactly one variant at a time (data Shape = Circle Float | 
  Square Float)

  Effect maps these to TypeScript:
  FP concept: Product type
  Effect construct: Schema.Struct or Schema.Class
  TypeScript result: Plain object or class instance
  ────────────────────────────────────────
  FP concept: Sum type
  Effect construct: Schema.Union of Schema.TaggedClass variants
  TypeScript result: Discriminated union with _tag
  ────────────────────────────────────────
  FP concept: Branded primitive
  Effect construct: Schema.brand()

  Community consensus on Class vs Struct

  From what I found across https://www.effect.solutions/data-modeling, the
  https://effect.website/docs/schema/classes/,
  https://dnlytras.com/blog/effect-ts, and
  https://dev.to/gcanti/functional-design-algebraic-data-types-36kf, there are
  two schools:

  1. "Class-first" (Effect's official examples lean this way)

  Use Schema.TaggedClass for every variant in a sum type. The _tag discriminant
  + instanceof + Match.valueTags gives you the closest thing to real pattern
  matching:

  class Circle extends Schema.TaggedClass<Circle>()("Circle", { radius:
  Schema.Number }) {}
  class Square extends Schema.TaggedClass<Square>()("Square", { side:
  Schema.Number }) {}
  const Shape = Schema.Union(Circle, Square)

  This is the ADT-as-classes pattern. Each variant is a Class, the union is the
  sum type. You get exhaustive matching via Match, Equal trait for structural
  equality, and _tag for discrimination. The
  https://github.com/Effect-TS/effect/pull/4736 further simplifies this, showing
   the community wants even less boilerplate for this pattern.

  2. "Struct-default, Class-when-needed" (pragmatic camp)

  Lytras captures this well: "I write my code using Effect-ts in an imperative 
  way. It's inspired by functional libraries...but it's not dogmatic. If 
  anything, sometimes using Classes is more convenient." Use Struct for plain
  validated data, promote to Class only when you need behavior (getters,
  methods) or nominal typing.

  What this means for our codebase

  Our schemas map cleanly to FP concepts:
  ┌────────────────────┬─────────────┬─────────────────────────────────────────┐
  │     Our schema     │ FP concept  │             Right construct             │
  ├────────────────────┼─────────────┼─────────────────────────────────────────┤
  │ CurveMethod        │             │ Already correct: Schema.Union of tagged │
  │ (std_dev |         │             │  Structs. Could use TaggedClass if we   │
  │ percentile |       │ Sum type    │ wanted Match integration, but we        │
  │ absolute)          │             │ destructure on type field directly —    │
  │                    │             │ works fine.                             │
  ├────────────────────┼─────────────┼─────────────────────────────────────────┤
  │ CheckOutcome (pass │ Sum type    │ Same — Schema.Union of tagged Structs.  │
  │  | fail)           │             │                                         │
  ├────────────────────┼─────────────┼─────────────────────────────────────────┤
  │                    │ Product     │                                         │
  │ JSONScores         │ type with   │ Schema.Class — correct, the one place   │
  │                    │ derived     │ it earns its weight.                    │
  │                    │ fields      │                                         │
  ├────────────────────┼─────────────┼─────────────────────────────────────────┤
  │ Curve,             │ Plain       │ Schema.Struct — no behavior, no         │
  │ CurvedScores,      │ product     │ discrimination needed.                  │
  │ ProblemScore, etc. │ types       │                                         │
  └────────────────────┴─────────────┴─────────────────────────────────────────┘
  The one place where the "Class-first" camp has a point we're not using: if we 
  ever needed Match.valueTags exhaustive matching on CurveMethod or 
  CheckOutcome, upgrading those union variants to TaggedClass would enable that.
   But currently we switch on .type / .status with plain if — simpler and
  sufficient.

  Bottom line: The community is split, but the split aligns with whether you're
  building an Effect-native application (where Match, Equal, _tag conventions
  permeate everything) vs. using Effect Schema as a validation layer (our case).
   For a validation/transformation layer, Struct-default is the pragmatic
  choice.
